安全不是一次设计出来的：从 v1 到 v4

左页看设计怎么长出来：每一格是「做法 → 被什么打脸 → 补上了什么」；右页才是今天的设计与证据。

v1

信模型

把 prompt 写成“只生成 SELECT”，模型返回什么就执行什么。

被打脸：UNION、多语句、可执行注释都能绕过；没有任何执行前检查。
补上只读账号 + 静态 guard（SQL 粗筛）
v2

只读账号 + guard

dw_reader（只读执行账号）只有 SELECT，再加单语句/只读/表列检查。

被打脸：挡写不挡读：合法 SELECT 仍可越权读/外带；集合运算与危险函数仍能钻。
补上安全 policy（AST 安全复查）：AST（SQL 拆成语法树）六关
v3

policy 六关

按类别拒绝 + 白名单放行 + 自动 LIMIT；拒绝不连库。

被打脸：错误形状不统一，策略拒绝的 retryable 边界容易被误读。
补上统一 ChannelError 16 码 / 3 class
v4 · 当前

三层防线 + 出口

guard / policy / dw_reader 各自拒绝，ChannelError 统一出口。

被打脸：真库只读验证此前缺位（现已实证 SHOW GRANTS / 1142）；语料有限，不代表所有攻击。
补上当前设计

三层防线，一个出口

不是“一道更严的关”，是三层独立防线（guard / policy / dw_reader）+ 一个统一出口。契约白名单是 policy 的输入；guard / policy / dw_reader 各自拒绝；ChannelError 负责出口。
图 22 · 策略内部六关（单语句 → 只读 → 表白/列白 → 无常量 → 排序/LIMIT → 收尾）；六关不是三层本身；拒绝不连库。
