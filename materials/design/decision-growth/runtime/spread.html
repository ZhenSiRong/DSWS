启动顺序不是设计出来的，是被假绿逼出来的

左页看设计怎么长出来：每一格是「做法 → 被什么打脸 → 补上了什么」；右页才是今天的设计与证据。

v1

sleep 30

固定等一会儿，库总会起来。

被打脸：慢、假绿（看着全绿其实没起）；库没起来也可能继续，失败后不知道停在哪。
补上depends_on
v2

depends_on 顺序

compose 按顺序拉容器，就算依赖完成。

被打脸：Started ≠ healthy；init 可能比库快，backend 可能没初始化就接客。
补上healthcheck
v3

healthcheck

存储给出健康信号，init 等 service_healthy。

被打脸：up 成功 ≠ 部署好；init 失败/一次性没验，端口/SSE 也没测。
补上失败停点 + init 退出 0 + smoke
v4 · 当前

失败停点 + 灰度验收

每级条件化，失败停下游前；init 一次性，smoke 8 步。

被打脸：失败注入打脸出 nuance：scale=0 时 compose 把 service_healthy 当空满足，停点靠 docker_init 180s 超时兜底；启动耗时不是设计承诺。

失败停在下游之前

不是盲等，是条件轮询 + 超时上限；失败停在下游之前。三存储 healthy → init 退出 0 → backend healthy → frontend；init 内部还有 2s 条件轮询与 180s 上限（[当前值]），不是纯 sleep。
图 27 · 启动顺序与失败停点：存储不 healthy 停 init 前；init 非 0 停 backend 前；backend 不 healthy 停 frontend 前。
E1 · 条件可读

compose config 通过

解析出 mysql/ES/Qdrant healthcheck；init 等 service_healthy；backend 等 init completed；frontend 等 backend healthy。

Exited (0) 才能放行

smoke 8 步

健康、init 退出码、端口、SSE 缓冲都要单独验；up 成功只说明容器建起来了。
