第 17 页 · 审纠错：一次重试能修好什么、修不好什么

前置

还原上一页：确认第 16 页的拆一刀已用 scripts/lab reset p16-before --yes 还原——否则第 2 步会变成 1 failed, 13 passed、没有 S6 PASS、probe mismatch: 3。

可执行自查：(cd backend && .venv/bin/python -m app.scripts.failures --check | tail -2) 应见 S6 PASS；不是就先 scripts/lab reset p16-before --yes 再往下。

第 1–5 步全离线：14 条单元测试、9 个失败场景、20 条纠错语料全在离线跑——不需要 MySQL / ES / Qdrant、不需要 .env、也不需要模型 key。只有第 6 步要真模型 + 开栈（可选，没配 key / 没起栈就跳过）。

在哪跑：命令都在仓库根目录、同一个终端里整段连续执行；括号是子 shell，跑完你还在仓库根目录。

这一页构建什么

把纠错（correct_sql）当成一次有上限的赌博来审：只重试 1 次、只对可重试错误生效、改出来的 SQL 必须重新过静态校验与安全策略。

怎么考核：本页是 L3（审）的最后一页。不是“把页面做完”，而是拆掉纠错后能说清：哪条判据抓到了、哪条没抓到。审过的标准不是“红变绿”，是写下“触发几次、成功几次、失败长什么样”，换个人重跑得到同一组数。

为什么“纠正成功”不能当判据：触发取决于模型是否生成可重试错误，不能稳定复现、不能当判据。

  • v1 演示没复现：deliverable/PRD-对照表.md 第 13 行，触发=true、纠正成功=false。
  • v2 单次复现过纠正成功态：deliverable/v2/README-v2.md:172；证据 deliverable/v2/evidence/v2-natural-correct-success.sse，故障注入样本 v2-correct-success.sse 另存作回归。

猜一猜

  1. 20 条纠错语料里，写着“重试后仍失败”的条目有几条——0 条、9 条、还是 11 条？
  2. 真实模型的“纠正成功”能稳定复现吗——判据能写“已修复 / 成功率 100%”，还是只能写“3 次里几次过”？

5
第 5 步：用原子工具看一层时间线、再停一次断点。 本页这一步只把 VizTracer 装进项目 backend/.venv（trace 要和项目依赖同一个解释器；它不改 uv.lock），--open 跑完自动开浏览器；pdb 是 Python 自带，不用装：
uv pip install --python backend/.venv/bin/python viztracer
backend/.venv/bin/python -m viztracer --open --min_duration 1ms -m pytest backend/tests/agent/test_correct.py -q
backend/.venv/bin/python -m pdb -m pytest backend/tests/agent/test_correct.py -q -s -k "proposes_a_new_sql"

看时间线：点 propose_correction 条带看 Wall Duration。--min_duration 1ms 约留 ≥1ms 的调用；收尾事件仍可能 <1ms，属正常。

缓冲陷阱：不加 --min_duration 会写满环形缓冲、丢早期数据——实测约 170 MB，浏览器打不开；嫌大可调 --tracer_entries。产物 result.json 落在仓库根，看完可删。

pdb 四连敲（第三条命令），进 pdb 后依次敲：

  1. b backend/app/agent/correct.py:183
  2. c
  3. p policy.max_attempts
  4. p error.retryable

三个陷阱：

  • 顺手敲 p attempts 会报 NameError——它是 graph 状态里的计数，不在这一帧（原因见「你应该看到」第 5 步）。
  • 直接按 q 退出，pytest 会记一条 1 failed, 13 deselected … BdbQuit——那是 pdb 中途退出的预期记录，不是你把测试弄坏；重跑整条 pytest 即回 14 passed。想留现场就按 c 跑完。
  • 别忘 -s：pytest 默认接管 stdin，省了会报 OSError；断点文件从仓库根写全路径，b app/agent/... 会报 not found。

更多工具卡（py-spy / scalene / DevTools / Studio）见 appendix/gui-debugging.md。

6
第 6 步：自己采多次（本步要真模型）。 判据是“触发几次、成功几次”，一次跑不出来。没配 key / 没起栈就跳过这步。

没 key 是预期：默认栈不配 key 时后端走确定性生成器、根本没有校正器（_build_corrector() 返回 None）。页内这个问题一次就过校验，只会采到“无需校正 3/3”，采不到“触发/成功”——这是预期，不是 bug。

要采先配：按 appendix/llm-endpoint.md 配 REBUILD_LLM_*，再 docker compose up -d --force-recreate backend 重启。变量缺一个或 key 配错都不算，先跑附录里的 scripts/llm_check.py 自检。

界面入口别混：只按第 13 页起整栈，默认是教学版 http://127.0.0.1:8080（改过 .env 就用你的 FRONTEND_HOST_PORT）；成熟版 http://127.0.0.1:8088 来自第 23 页第 2 步的 docker run -p 127.0.0.1:8088:80，不是 compose 起的。

同一问题「查询销售额大于平均销售额的商品」点 3 次；或手动发 3 次：

curl -sN -X POST http://127.0.0.1:8080/api/query -H 'content-type: application/json' -d '{"query":"查询销售额大于平均销售额的商品"}'

端口别混：curl 走教学版界面入口 FRONTEND_HOST_PORT（默认 8080）；nginx 在容器内把 /api/ 反代到 backend:8100。

端口 是谁 哪来的
8080 教学版界面 第 13 页 compose 起整栈
8088 成熟版界面 第 23 页第 2 步 docker run -p 127.0.0.1:8088:80
8100 后端 API 直连才用 BACKEND_HOST_PORT（默认 8100）

8100 与 8080/8088 两个界面无关。把每次结局填进五类表（分母 = 触发校正次数 = 触发并成功 + 触发失败，不是提问次数；3 问里触发 2 次、成功 1 次就写 1/2）：

无需校正 触发并成功 触发失败 校验红未校正 传输失败

对账

  • 猜 1：0 条。 20 条里 11 条 retryable: true + expect: "corrected"，9 条 retryable: false + expect: "rejected"。

两个标记什么意思：rejected 不是“重试后仍失败”，是根本不进重试（策略拒绝 / 多语句 / 写操作 / 空 SQL 这类，重试等于给注入开一次口子）；corrected 也只说“这条错单该进校正”，不等于校正会成功。

为什么成功率是假的：eval/build_datasets.py 用 contracts/errors.yaml 的 retryable 逐条校验这张表（expect 与 retryable 对不上就报错退出）——语料里一条重试结局都没有，拿它算“成功率”（11/20 或 11/11）都是假的。

  • 猜 2：不能。 两个样本结论不一样——成功率是抽出来的数，不是“修好了”。

样本 A（deliverable/PRD-对照表.md 第 13 行，真实云端模型）：validate 红 → correct 真跑 16.31s → 改写后列名仍不在契约，记的是“触发=true、纠正成功=false”。v1 视频/SSE 未随仓库分发，仓库里能核对的同类证据在 deliverable/v2/evidence/。

样本 B（eval/FINDINGS.md）：§3.1 同一问题第一次 error → SQL_UNKNOWN_TABLE，随后 3 次全成功——4 次里 3 次，不是“修好了”；§2 另一次 8 题 × 3 次采样记的是 5/5——那是 24 次运行里的 5 次机会，不能外推成“成功率 100%”。

判据只能写“多次采样（trials>=3）+ 成功率 + 失败分类”，不许写“已修复”，分母是“触发校正的次数”，不是全部提问。

计数口径（eval/live_probe.py，与第 6 步同一套五类）：无需校正 no_correction_needed / 触发并成功 correction_success / 触发失败 correction_fail / 校验红但没进校正 validate_fail_no_correction，另有传输失败 transport_error；成功率分母同为 success+fail、不含后两类。

怎么跑：它要跑着的服务和模型 key；本页第 6 步只教你怎么采，采完按第 6 步五类表记。端点怎么配、怎么自检：见 appendix/llm-endpoint.md。

  • 一次重试的边界在契约里，不在代码里。 contracts/errors.yaml 的 correction 段：max_attempts: 1、revalidate: true、revalidate_with: [guard, policy]。

可重试名单：retryable: true 的只有 6 个码——SQL_SYNTAX / SQL_UNKNOWN_COLUMN / SQL_UNKNOWN_TABLE / SQL_CONSTANT_PROJECTION / SQL_MISSING_ORDER_BY / SQL_MISSING_LIMIT。

SQL_REJECTED 为什么不可重试：拿被策略拒掉的 SQL 去问模型“改一下”，等于给注入开重试口子。上一页拆掉列存在校验、SQL_UNKNOWN_COLUMN 退化成 SQL_REJECTED 之后，纠错连启动的机会都没有。

两道关：校正改出来的候选 SQL 必须重过两道关，原始 SQL 一直留在 detail.original_sql。

  • “降级为拒答”不是失败，是正确结局。 上下文里没有语义等价的字段时，校正器拒答、原始错误原样上报（test_corrector_refusal_keeps_the_original_error 钉的就是“根因没变，错误也不该变”）；把拒答当失败、硬造一个列名，才是事故。

你现在拥有：一次有上限的纠错闭环——次数、重校验、可重试名单全在契约里；以及一条判据：校正成功要按多次采样写，不按单次演示写。

拆一刀（L3 级考核）

级考核不看本页做完没有，只看拆完你能说出“哪条判据抓到了、哪条没抓到”。

把纠错关掉：打开 backend/app/agent/correct.py，找到校正的唯一入口 def propose_correction，在 policy = contract.correction 这一行后面插 4 行（缩进 4 格）。任何错误都直接返回“校正失败”，有校正器 / 可重试 / 契约允许这三条触发条件全部短路：

    # 拆一刀：关掉校正闭环——任何错误都不再产出候选 SQL
    return CorrectionProposal(
        attempted=False, ok=False, error=error, note="拆一刀：校正已关闭"
    )

Ctrl+S 保存，重跑三条判据（输出为节选：pytest 只留汇总行；PYTHONUNBUFFERED=1 让管道里的输出顺序和终端一致；秒数会变）：

backend/.venv/bin/python -m pytest backend/tests/agent/test_correct.py -q
(cd backend && PYTHONUNBUFFERED=1 .venv/bin/python -m app.scripts.failures --check) 2>&1 | tail -5
PYTHONPATH=backend backend/.venv/bin/python eval/probe_correction.py | tail -1

5 failed, 9 passed in 0.14s
  corrected            期望 result               实际 SQL_SYNTAX
FAIL: 1 项不符合预期
{"total": 20, "mismatch": 0}

这是三件事：

  • pytest 5 条红：它们都在断言“校正入口会产出候选 / 把校正器的拒答原因带回来”，入口一短路全红。
  • 失败矩阵 9 个场景只红 corrected 一格：它是唯一靠“校正成功”才拿得到 result 的场景；另外两个可重试失败（sql_syntax / sql_unknown_column）本来就以原码收尾。
  • probe 的 20 条语料照绿：它量的是 guard/policy 发什么码，不量校正做没做。

级考核要的答案就在这里：单元判据和失败矩阵抓到了，语料判据没抓到。

还原并回绿：reset 会先拍一张 pre-reset-… 安全快照；第 1 步若换过快照名，这里的名字也要同步换。只贴末行，跑完回到 14 passed in 0.11s + S6 PASS（同第 2、3 步）：

scripts/lab reset p17-before --yes
backend/.venv/bin/python -m pytest backend/tests/agent/test_correct.py -q | tail -1
(cd backend && .venv/bin/python -m app.scripts.failures --check | tail -1)

结论：纠错只负责一件事——把“可重试的失败”捞回来一次；捞回来就是 corrected 的 result，捞不回来就是最初那个错码。

L3 四页的判据合起来看：P14 的检索黄金集、P15 的 10 题基线、P16 的 20 条错单码、P17 的 corrected 场景，各量一层，才是“机器靠不靠谱”的答案。真实模型的成功态只能靠多次采样，单次演示会骗人。
