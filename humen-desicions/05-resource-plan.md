# 环境资源与工具利用方案（评审稿）

## 0. 结论先行

这台机器的瓶颈**不是 CPU，是内存**：12 核，但 14G 里只剩 **3.8G 可用**，无 GPU，磁盘 41G。

所以本方案的三条硬规则：

1. **能机械判定的，绝不调模型**（把 CPU 用在构建、测试、门禁上）。
2. **模型按“贵/便宜/免费”分层使用**，贵的只做决策，便宜的去跑量。
3. **并发上限 = 2 个学生 agent + 1 个构建**，再多会先被内存拖死。

预算：Seedream Lite **12/34 张**、CodeBuddy **8 次**、DeepSeek **约 100 次**、Seedream Pro **0 次**。

## 4. 并发与内存预算

按单进程粗估（保守值）：

| 进程 | 内存 | 说明 |
|---|---|---|
| CodeBuddy 学生（1 个） | 0.5–0.8G | 读 PDF + 跑 shell |
| Chrome headless | 0.3–0.5G | 截图/录屏 |
| WeasyPrint 全量构建 | 0.4–0.6G | 24s 一次 |
| pytest 全量 | 0.3G | 26s 一次 |

**排班：**

| 时段 | 并行内容 | 内存占用 |
|---|---|---|
| A | 2 个学生 + 1 个教材构建 | ≈ 1.6–2.2G |
| B | 1 个学生 + 校正基准（本地） | ≈ 1.0–1.5G |
| C | 视频录制（独占） | ≈ 1.0G |

不要出现「3 学生 + 视频 + 构建」同时跑；可用内存 3.8G 撑不住。

## 6. 并行泳道

```
主路径   P0 基线 ─► P1 审计 ─► P2 改写 ─► P3 学生验证 ─► P6 终审
旁路 A   C3 校正基准（本地 DeepSeek，随时可跑）──────────┘
旁路 B   P5 部署（远程 5051，一次窗口）─► P4 视频（等部署完成）
```

- **旁路 A** 不依赖教材，今天就能跑；它决定“校正准确性”这条第一判据。
- **旁路 B** 的构建放到远程，本地只发命令和验收，省内存。
- P4 必须等 P5；P3 必须等 P2 出 PDF。

## 7. 缓存与复用

| 对象 | 做法 | 省下什么 |
|---|---|---|
| `uv` | 保留 1.2G 缓存，`uv run --offline` | 每次建环境的时间与网络 |
| `backend/.venv` | 已含 langgraph，不重建 | 数分钟 |
| `style-lab/.venv` | WeasyPrint 70 固定 | 版本排障 |
| PDF 文本 | `pdftotext` 落盘一次，之后只 `grep` | 避免重复解析 7MB |
| 插图 | content JSON 幂等；通过后不再生成 | Lite 配额 |
| worktree | 一个模板 + `git clean -fdx` 复位 | 避免重复建树 |
| Docker | 远程分层缓存，只重建变更层 | 带宽与时间 |
| Chrome | 每次新 profile，避免污染 | 截图稳定性 |

## 8. 反浪费清单

1. 门禁能判的，不调模型。
2. 图过了就不再生成；要改只改 JSON/文案。
3. 不每改一章就重建 PDF，攒批构建。
4. 不重复建 worktree。
5. 不超过 2 个并发学生。
6. 不把整本 PDF 塞进上下文。
7. 视频录制独占机器。
8. Pro 不调用，Flash 不开通。
9. 不在本地跑 Docker 全量构建（放远程）。
10. 不为“确认一下”重复跑已经绿的测试。

---

## 9. 资源不足时的降级顺序

**先减并发 → 再减插图数量 → 再降视频帧率/时长 → 最后才降模型档位。**

模型档位一降，“学生能否学会”的结论就不成立，必须最后动。

---

## 10. 需要你拍板的 6 个参数

1. **并发上限**：2 个学生 + 1 构建（推荐），还是 3 个学生？
2. **Playwright**：装 `playwright-core` 用系统 Chrome（推荐），还是改用 Chrome DevTools 脚本？
3. **插图预算**：12 张（推荐），还是压到 8 张？
4. **视频规格**：1080p60（推荐，文件约 30–60MB），还是 1080p30（更小）？
5. **重活分流**：Docker 构建与全量测试放远程（推荐），还是全在本地？
6. **评审次数**：人工只评审 2 次（推荐：本方案 + 终审），还是每阶段一次？
